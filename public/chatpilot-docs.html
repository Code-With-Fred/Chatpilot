Part One — Running the Business

How ChatPilot works, in plain English.

No code in this part. If you just need to onboard a client, read leads, or fix something that broke, start here.

1.1What ChatPilot actually is

ChatPilot sells one thing: a chat bubble that lives on a business's website and answers their customers' questions automatically, 24/7.

Think of it like hiring a receptionist who never sleeps, never takes a day off, and already knows everything about the business — their hours, their prices, their services — because you told it all of that ahead of time.

1.2The three pieces

Everything lives in one project, and it breaks down into exactly three things:

PieceWhat it isWho uses it
Landing pageThe website that sells ChatPilotPotential customers, browsing
The widgetThe actual chat bubble that goes on a client's siteTheir website visitors
Admin dashboardWhere you manage everythingYou

The widget — the actual product

This is the one thing you're really selling: a small chat bubble that appears in the bottom-right corner of a business's website. You give each client one line of code to paste into their site:

<script src="https://your-domain.com/widget.js" data-client="their-business-slug"></script>

That's it. That single line draws the bubble, loads that business's name and greeting, lets visitors chat with an AI that only knows about that business, and shows a "Leave your details" button so visitors can hand over contact info even without typing a full conversation.

A visitor never knows the bubble came from "ChatPilot" behind the scenes — aside from a small, unobtrusive "Powered by ChatPilot" credit at the bottom of the panel — it looks and talks like it belongs to that business.

The admin dashboard — your control panel

A single password-protected page (your admin key) where you add a business, get their embed snippet, preview their widget, edit their info any time it changes, and see every lead they've captured — with stats and a CSV download.

1.3Onboarding a new client, step by step

  1. A business signs up and pays.

  2. Open /admin.html and log in with your admin key.

  3. Fill in the "Add a new business" form. Business name is the only required field, but the more you fill in, the smarter their widget sounds:

    • About the business — a couple of sentences on what they do
    • Services / products — what they offer
    • FAQs — common questions and answers, one per line is fine
    • Hours and booking info — how someone books with them
    • Contact email — where their leads should be sent
    • Brand color and greeting — how the widget looks and opens

  4. Click Create client. A row appears in the clients table with their embed snippet already written out.

  5. Click Preview to try the widget yourself, exactly as their visitors will see it.

  6. Click Copy snippet and send that one line to the client, or paste it into their site yourself. It goes anywhere before the closing </body> tag — WordPress, Wix, Squarespace, Shopify, Webflow, or hand-built, no differently.

  7. Done. Their widget is live.

1.4What happens when a visitor uses the widget

  1. The chat bubble appears in the corner of the site.

  2. After a few seconds, if they haven't clicked it, a small message bubble pops up on its own inviting them to chat — standard behavior for chat widgets, nudging engagement instead of waiting silently.

  3. If they type a question, the AI answers using only what you entered for that business. It won't invent prices or policies you didn't give it — if it doesn't know something, it says so and points them to the details form instead of guessing.

  4. If they click "Leave your details," they fill in name + email/phone + a short message, captured as a lead immediately — whether or not they ever typed a chat message.

1.5Where leads end up

Every lead shows up in two places: the admin dashboard under Leads (filterable by client, downloadable as CSV for Excel/Sheets), and the client's own inbox — automatically, but only if you've set up email sending. If you haven't, leads still land safely in the dashboard; they just don't get emailed out.

1.6Editing a client's info later

Business hours change, prices change, new FAQs come up. In the clients table, click Edit on any client — their existing info loads back into the form, make your changes, click Save changes. Their live widget uses the new info on the very next message; no reinstall needed on their site.

1.7Reading the stats

At the top of the dashboard: Total clients (how many businesses are using ChatPilot right now), Total leads captured (across every client, all time), and Leads in the last 7 days — a quick pulse check on recent activity.

1.8Setting up lead emails (optional)

By default, leads only show up in your dashboard. To have them automatically emailed to each client, give ChatPilot an email account to send from — a one-time setup in the .env file:

SMTP_HOST=smtp.yourprovider.com
SMTP_PORT=587
SMTP_USER=you@yourdomain.com
SMTP_PASS=your-email-account-password-or-app-key
LEAD_NOTIFY_FROM=you@yourdomain.com

Most email providers (Gmail, Zoho, Outlook, your domain host) can give you these SMTP details — search "[your provider] SMTP settings." Once set and the server restarted, every lead is emailed to that client's contact email automatically, in addition to showing up in your dashboard.

1.9Troubleshooting

The chat isn't answering, it just says something went wrong.

The AI needs a Claude API key to work. Open .env, check that ANTHROPIC_API_KEY is a real key (not the placeholder text) from console.anthropic.com, then restart the server.

I forgot my admin key / lost access to the dashboard.

It's in your .env file under ADMIN_KEY. Open that file directly to see it, or set a new one and restart.

A client says their leads aren't emailing to them.

Check two things: their contact email is filled in for that client in the dashboard, and the SMTP_* settings are filled in in .env. Without both, leads still land safely in the dashboard — they just won't auto-email.

I deleted a client by mistake.

Deleting a client also deletes their leads — there's no undo. The delete button always asks you to confirm first for exactly this reason.

1.10A short glossary

Client
A business paying for ChatPilot; one row in your dashboard.
Slug
The short web-safe id ChatPilot generates from a business's name (e.g. "Bright Smile Dental" → bright-smile-dental). It's what goes in their embed snippet.
Embed snippet
The one line of <script> code a client pastes into their site.
Lead
A name + contact info someone left in a client's widget.
Admin key
Your password into /admin.html.
Part Two — Technical Reference

The architecture, the data, the API.

For a developer working on the code. Assumes no prior familiarity with this codebase, but does assume you can read JavaScript.

2.1Architecture

Nothing in a browser — not the landing page, not a client's widget, not the admin dashboard — ever talks to Anthropic directly. Everything routes through server.js, the only place holding the Anthropic API key.

2.3The database

Two tables, in data/chatpilot.db (SQLite, via better-sqlite3).

clients

ColumnMeaning
idRandom hex id, e.g. 946f305f52480f76
slugURL-safe name, e.g. bright-smile-dental — used in the embed snippet
business_nameDisplay name
about_text, services, faqs, hours, booking_infoEverything the widget's AI is allowed to know
contact_emailWhere lead notification emails go
brand_colorHex color, styles the widget
greetingFirst message shown in the widget
created_atISO timestamp

leads

ColumnMeaning
idRandom hex id
client_idForeign key → clients.id, ON DELETE CASCADE
name, email, phone, messageWhatever the visitor entered
created_atISO timestamp

ON DELETE CASCADE means deleting a client automatically deletes their leads at the database level — db.deleteClient() doesn't need to, and doesn't, manually clean up leads itself.

lib/db.js wraps all of this in plain functions — createClient, getClientById, getClientBySlugOrId, listClients, updateClient, deleteClient, createLead, listLeads, getStats — nothing outside that file writes raw SQL.

2.4Building a client's prompt

lib/clientPrompt.js takes a client row and produces a system prompt like this:

You are the AI assistant for Bright Smile Dental, installed on their
website by ChatPilot.

About the business:
A friendly dental clinic.

Services / products:
Cleanings, whitening, checkups
...

Rules:
- Only answer using the information above. Never invent facts...
- If you don't know something, say so honestly and point the visitor
  to "Leave your details"...

This is why a client's widget won't make up prices or policies: the model is explicitly told its knowledge is limited to what's in that prompt, and to defer to the lead form for anything else.

2.5API reference

All request bodies are JSON. All responses are JSON except the CSV export.

Public — landing page

EndpointBodyReturns
POST /api/chat{ messages: [{role, content}] } (1–40){ reply }

The landing page's own sales demo — a fixed persona, not tied to any client.

Public — every embedded widget

/api/widget/:clientId/... — :clientId accepts either a client's slug or its id. No auth: a slug isn't a secret, the same way an Intercom "app id" isn't — it only unlocks that one client's own data. Unknown :clientId → 404.

EndpointBodyReturns
GET /config—{ businessName, greeting, brandColor }
POST /chat{ messages: [...] }{ reply }
POST /lead{ name, email?, phone?, message? } (email or phone required){ ok: true }

Protected — the admin dashboard

/api/admin/... — every request needs an x-admin-key header matching ADMIN_KEY in .env. Missing or wrong key → 401.

EndpointBodyReturns
GET /stats—{ totalClients, totalLeads, leadsLast7Days }
GET /clients—{ clients: [...] }
POST /clientsclient fields, below201 + { client }
GET /clients/:id—{ client } or 404
PUT /clients/:idany subset of client fields{ client } — only sent fields change
DELETE /clients/:id—{ ok: true } — cascades to their leads
GET /leadsquery: ?clientId=&limit=&offset={ leads: [...] }
GET /leads/:clientId/export.csv—CSV file download

Client fields (all optional except businessName): businessName, aboutText, services, faqs, hours, bookingInfo, contactEmail, brandColor (hex, e.g. #d4ff00), greeting.

Everything else

GET /health → { ok, keyConfigured, adminConfigured } — useful for uptime checks. Unmatched /api/* routes → 404. Any unhandled error in a route is logged with full detail server-side and returns 500 with a generic message to the client — internals never leak in a response.

2.6Security measures, and why each exists

  • Input validation (zod) — every request body is checked against a schema before it reaches the database or the AI. Bad input gets a clear 400, not a stack trace or a bad database write.
  • Rate limiting — a generous baseline on all /api/* routes, tighter limits specifically on /chat (costs money per call) and /lead (spam-prone, unauthenticated).
  • Constant-time admin-key comparison — a plain === leaks timing information proportional to how many characters match; lib/auth.js hashes both sides first and compares with crypto.timingSafeEqual.
  • No native SQL string-building — all queries are parameterized prepared statements via better-sqlite3.
  • Static file scope — only index.html and everything under public/ are servable over HTTP. server.js, routes/, lib/, and the database file are never reachable by URL, even though they live in the same project folder.
  • Shadow DOM widget — widget.js renders inside a Shadow DOM, so a client's own site CSS can't break the widget's look, and the widget's styles can't leak onto their page.
  • Helmet security headers on every response. Content-Security-Policy is deliberately left off, because index.html / admin.html / widget.js all use inline <script>/<style> — a strict CSP would need per-request nonces to allow that.

2.7Errors & logging

Every async route is wrapped in asyncHandler (lib/asyncHandler.js), so a thrown error or rejected promise is forwarded to Express's error middleware instead of crashing the process or hanging the request. One central handler at the bottom of server.js logs the full error with lib/logger.js (structured JSON, one line per event) and always returns a generic { error: "Internal server error" } to the client — internals never leak in a response.

lib/env.js runs once at startup and logs every configuration problem — missing API key, missing admin key, invalid port, half-configured SMTP — clearly and all at once, instead of each one surprising you individually the first time it's hit.

2.8Running it

npm install
npm start        # or: npm run dev  (restarts on file changes)
npm test          # 34 tests, node:test + supertest, in-memory database

server.js exports the configured Express app and only calls app.listen() when run directly (require.main === module). Tests require('../server') to get the app without binding a real port, and drive it with supertest instead — set process.env.DB_PATH = ':memory:' before requiring it for a clean, isolated database per test file.

2.9Deploying

Any host that runs npm install && npm start works: Render, Railway, Fly.io, or a plain VPS with pm2/systemd + nginx for TLS.

Required environment variables in production: ANTHROPIC_API_KEY, ADMIN_KEY. Set TRUST_PROXY=1 if the host sits behind a reverse proxy (Render/Railway/Fly.io all do) — this makes rate limiting and logging use the real client IP from X-Forwarded-For instead of the proxy's own IP. Leave it unset on a bare/direct deployment, where trusting that header would let clients spoof their IP.

The SQLite file (data/chatpilot.db) must live on persistent storage — if your host wipes the filesystem on every deploy, mount a persistent disk at data/ or every deploy will erase all clients and leads.

2.10Extending this

  • Multi-user admin accounts (instead of one shared ADMIN_KEY) — would replace lib/auth.js's key check with real sessions/JWTs and a users table in lib/db.js.
  • Lead status tracking (New / Contacted / Closed) — add a status column to leads, a PATCH /api/admin/leads/:id route, and a dropdown in admin.html's leads table.
  • Per-client analytics (messages per day, most-asked questions) — log chat events to a new table from routes/widget.js's /chat handler, then chart from it.
  • Swapping the database — everything database-related is isolated in lib/db.js; nothing else writes SQL, so swapping SQLite for Postgres later means rewriting that one file, not the routes.
